# AEP v5：以產品目的驅動的自主研究

日期：2026-09-11
狀態：已接受；依使用者要求實作原生指引，驗證與安裝結果見[實作 audit](../audits/2026-09-11-aep-v5-purpose-research.md)
來源：[MITS 產品聚焦觀察](../lessons/2026-09-11-mits-product-focus-observation.md)

## 要補足的能力

使用者提出「auto deep research for purpose」，指出這是 4.x 缺少的能力。重點是讓 agent 在推薦方向、選擇 benchmark 或投入實作前，主動建立足以支持決策的 context。研究回答「我們為何值得做這件事、證據支持到哪裡、哪個未知會改變選擇」，不以報告篇幅、來源數或搜尋輪數代表完成。

MITS 這輪原先推薦一個保留的候選功能，經使用者追問才回查研究、修正優先序。後續產品聚焦則做出了較好的行為：讀取現有目的與觀察、查核原始資料、辨別外部評測涵蓋範圍、提出可驗證的比較。這是本概念的實際動機，尚不是新指引有效性的實驗結果。

## 自主性與研究深度

當產品目的、推薦依據、方案適用性或評測代表性存在會改變決策的缺口時，agent 自主展開研究。來源已充分、只是已知範圍的修正時，可直接沿用有效 context。先指出缺口與待決事項，再依所需證據選擇查閱歷史、官方文件、原始論文／資料／實作，或執行最小實驗。

使用者的產品意圖不能靠搜尋替代。若缺少會影響選擇的偏好，提出精簡問題，同時推進不依賴答案的工作。保留待定狀態；不把「傾向某 benchmark」當成已接受的目標、門檻或切換。

研究停止於足以選擇、排除、延後或指定下一個實驗的時點。若新增來源不再改變選擇，收斂已知與未知；若缺的是實際行為證據，銜接 prototype，而非繼續用更多文章代替觀察。

## 決策需要的 context

依問題選擇保留以下資訊，不要求固定表格：

- **目的與受益者：**誰遇到什麼問題，現在如何處理，改善後可觀察的差異。
- **決策問題與替代方案：**包含維持現狀；哪些結果會改變推薦。
- **證據與適用邊界：**主張的原始來源、版本／日期、方法、樣本與限制；分開事實、推論、假設和使用者偏好。
- **反證與缺口：**找可能推翻偏好方案的資料；歷史規劃不等於現有能力，別的系統成績不等於本產品效果。
- **下一個可觀察驗證：**驗證操作、對照、成功／失敗含義、成本與尚未決定的條件。

選 benchmark 時，額外檢查它與產品成果的映射、沒有涵蓋的能力、資料與評分方式、模型／工具／預算可比性、資料洩漏、重現條件及成本。先建立可比較的前瞻契約，保留歷史結果原意；不能靠換指標把舊失敗改寫成成功。

## 接回 AEP 的流程與目錄

```text
使用者目的／目前 context
  → 找出影響決策的證據缺口
  → 按需深入研究、比較及查反證
  → 仍需行為證據時做 prototype
  → 收斂建議、未知與可驗證的下一步
  → 在既有授權下更新 roadmap／decision／change
  → 有實作需求時銜接 implement → validate → deliver
```

下游研究與提案可保留在 `docs/research/`、`docs/design/` 並引用原始資料；持久產品方向與接受的取捨回到配置的 roadmap／decisions，行為契約與工作回到 ledger，執行教訓回到 lessons。連結與版本建立可追溯性；任意外部研究內容不會因被引用就自動納入 Rust 的 fingerprint enforcement。

「auto」由 working agent 判斷何時研究及深度。CLI 提供可發現的指引、records 和既有檢查，不新增語意路由器、模型呼叫或固定 gen-eval 流程。外部研究工具、模型與 subagent 依可用能力及既有授權選用，概念本身不要求新增供應商相依。

入口採用既有 roadmap／design：研究方法集中於 `roadmap/references/purpose-research.md`，使用者意見到 canonical context 的交接集中於 `roadmap/references/product-context.md`。roadmap、design 與進度解讀指引在需要時導向它們。保留八個入口與原有 description；不新增獨立 research skill 或語意路由命令。

## 建議、使用者意見與自主落檔的交接

使用者補充：「給完建議應該詢問意見之後應該自主把 product context 做好」。這個成果由 `roadmap → design` 承接；研究支援決策，reflect 只在有執行教訓需要沉澱時使用，並非產品轉向的必經入口。

先提出有證據的建議、主要取捨與真正需要使用者決定的問題。收到足夠明確的方向後，在同一任務內自主完成相關文件與連結，不再要求使用者逐項授權寫 roadmap、ADR、design 或 work record。若仍有未決部分，保存其狀態並完成已明確的內容；使用者的普通回饋不自動等於接受所有替代方案、benchmark 門檻或實作範圍。

| 要保存的內容 | 5.0 責任 | 下游配置的典型位置 |
| --- | --- | --- |
| 產品目的、主要使用者、問題、成功成果、優先序、journey／系統關係 | roadmap 維護 product context | `project-roadmap/` 的相關 plans／journeys／architecture 文件 |
| 選擇及原因、替代方案、來源、適用範圍、取代哪些舊決策 | roadmap 維護 decision，按目前授權接受或取代 | `project-roadmap/decisions/` |
| 研究推導、設計方案、介面、未知、benchmark 對照與 prototype 結果 | design 收斂設計 | `docs/design/`，必要時引用 `docs/research/` 的來源整理 |
| 已接受行為、場景、驗證契約及實作範圍 | design 建立／連結 change；有確定工作才建立 story | `project-ledger/changes/<id>/`、`project-ledger/stories/` |
| 本次操作中學到、下次值得重用的事情 | 按需 reflect | `lesson-learned/`；規則採納另循既有流程 |

Product context 是這些 canonical 文件及其連結共同構成，不重建 v4 的單一大型 product-context 檔案。Draft 到 accepted 的轉換要依已知使用者意圖與權限記錄 attribution；已接受且不可改寫的歷史用新決策取代或補充。設計接受後且實作在授權範圍內，繼續 `implement → validate → deliver`；純方向／設計請求則以完成分類、連結與可接續的契約作為交付。

完成時核對受影響文件的一致性、舊新決策連結、未決問題，以及適用的 `aep check`／`aep spec check`。結構通過不證明方向正確；回報採納了哪些使用者意見、更新了哪些 canonical 位置、下一步還缺什麼。

## 如何驗證這個概念

以真實或隔離情境觀察：使用者提出偏好的技術／benchmark，但證據不足；舊研究的結論與目前產品目的不一致；來源已完整而無需深入研究；目的缺少關鍵人類偏好。

看 agent 是否在推薦前識別關鍵缺口、查核而非複述舊結論、分辨假設與已接受方向、用反證修正推薦、適時停止研究，以及把結果接回正確目錄與後續工作。評估錯誤推薦、遺漏的決策條件與額外成本，不以文件數或固定研究步驟作為成功條件。指引格式檢查不能代替這種行為觀察。
