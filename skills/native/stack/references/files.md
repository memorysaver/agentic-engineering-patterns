# Stack files

Apply these blocks in order after `aep init` (step 4 of `aep --skill stack`). Replace `__PROJECT__` with the project name. *Write* creates or replaces the file with the block. *Merge into* merges the JSON object into the file: objects merge key by key, any other value replaces the existing one, keys not named stay as they are. *Append to* adds each line of the block that the file does not already contain, at its end. The written files are already formatted the way `vp check` expects; the merged JSON is sorted by the one `bun run format` in step 5.

AEP's CI applies these blocks mechanically to the pinned scaffold and runs the starter checks; keep the headings in the form `### Write`, `### Merge into` or `### Append to` followed by the path in backticks.

## Toolchain and checks

The root Vite+ configuration keeps the scaffold's settings and adds three things. `resolve.tsconfigPaths` lets `vp test` at the root resolve each package's own path aliases (the web app imports `@/…`). `run.cache.scripts` caches the workspace's `package.json` scripts when they run through `vp run`; Vite+ caches only tasks defined in `vite.config.ts` by default, which is why a second run hit nothing before. The ignore patterns keep `vp fmt` and `vp lint` away from the AEP stores (`.aep/`, `project-ledger/`, `project-roadmap/`, `project-rules/`, `lesson-learned/`, `docs/`), generated migrations and `AGENTS.md`: the `aep` CLI writes those files, and reformatting them would change record digests.

## Account-free local run and guarded deploy

`bun run dev` runs the infrastructure package's `dev` script: it completes the local env files, then starts `alchemy dev` with `CI=true` and placeholder Cloudflare values. alchemy 2 demands both values even when every resource is local; with `CI` set it takes credentials only from the environment and never reads a `~/.alchemy` profile, and placeholders set in the script also override any real token exported in the shell. `ALCHEMY_STATE=local` selects local state. `ALCHEMY_HOME=.alchemy/home` keeps alchemy's logs and its empty `default` profile directory in the ignored `packages/infra/.alchemy/home/` instead of the user's `~/.alchemy`, and `ALCHEMY_TELEMETRY_DISABLED=1` stops it writing an anonymous ID to `~/.alchemy/id`, which ignores `ALCHEMY_HOME`. Only `dev` sets them: `deploy` and `destroy` keep reading the owner's real profile.

### Merge into `packages/infra/package.json`

```json
{
  "scripts": {
    "dev": "bun ../../scripts/local-env.ts && ALCHEMY_HOME=.alchemy/home ALCHEMY_TELEMETRY_DISABLED=1 CI=true ALCHEMY_STATE=local CLOUDFLARE_ACCOUNT_ID=00000000000000000000000000000000 CLOUDFLARE_API_TOKEN=local-placeholder alchemy dev",
    "deploy": "bun ../../scripts/alchemy-guard.ts deploy",
    "destroy": "bun ../../scripts/alchemy-guard.ts destroy"
  }
}
```

The stack keeps its state under `packages/infra/.alchemy/` unless a deploy selects the Cloudflare state store. The scaffold's `Cloudflare.state()` bootstraps a state-store Worker in the account even for `alchemy dev`, so a local run with it contacts Cloudflare.

### Write `packages/infra/alchemy.run.ts`

```ts
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import "varlock/auto-load";

// Local state (files under .alchemy/, ignored by Git) unless a deploy selects the
// Cloudflare state store: the scaffold's Cloudflare.state() creates a Worker in the
// account even for `alchemy dev`. scripts/alchemy-guard.ts sets ALCHEMY_STATE for deploys.
const state =
  process.env.ALCHEMY_STATE === "cloudflare" ? Cloudflare.state() : Alchemy.localState();

export const db = Cloudflare.D1.Database("database", {
  migrations: "../../packages/db/src/migrations",
});

export const server = Cloudflare.Worker("server", {
  main: "../../apps/server/src/index.ts",
  compatibility: {
    flags: ["nodejs_compat"],
  },
  env: {
    DB: db,
    CORS_ORIGIN: Config.String("CORS_ORIGIN"),
    BETTER_AUTH_SECRET: Config.Redacted("BETTER_AUTH_SECRET"),
    BETTER_AUTH_URL: Cloudflare.Worker.URL,
  },
  dev: {
    port: 3000,
  },
});

export type ServerEnv = Cloudflare.InferEnv<typeof server>;

export default Alchemy.Stack(
  "__PROJECT__",
  {
    providers: Cloudflare.providers(),
    state,
  },
  Effect.gen(function* () {
    const serverWorker = yield* server;
    const webWorker = yield* Cloudflare.Website.Vite("web", {
      rootDir: "../../apps/web",
      compatibility: {
        flags: ["nodejs_compat"],
      },
      env: {
        VITE_SERVER_URL: serverWorker.url.as<string>(),
      },
      dev: {
        port: 3001,
      },
    });

    return {
      web: webWorker.url,
      server: serverWorker.url,
    };
  }),
);
```

The scaffold already writes `apps/server/.env` and `apps/web/.env` with a random `BETTER_AUTH_SECRET`, but without `NODE_ENV`, so the local server reports itself as `production`. The env-file generator writes the two files when they are missing (a fresh clone or worktree), so nobody copies secrets around, and adds `NODE_ENV=development` to an existing file that lacks it. It never changes another line.

### Write `scripts/local-env.ts`

```ts
// Writes the ignored local env files that `bun run dev` needs when they are missing, and
// adds NODE_ENV=development to an existing file without it. Other lines are kept.
// No Cloudflare account is involved: the secret is random and every URL is localhost.
import { existsSync, readFileSync, writeFileSync } from "node:fs";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";

const root = join(dirname(fileURLToPath(import.meta.url)), "..");
const secret = Array.from(crypto.getRandomValues(new Uint8Array(32)), (b) =>
  b.toString(16).padStart(2, "0"),
).join("");
const files: Record<string, string[]> = {
  "apps/server/.env": [
    "NODE_ENV=development",
    `BETTER_AUTH_SECRET=${secret}`,
    "BETTER_AUTH_URL=http://localhost:3000",
    "CORS_ORIGIN=http://localhost:3001",
  ],
  "apps/web/.env": ["NODE_ENV=development", "VITE_SERVER_URL=http://localhost:3000"],
};
for (const [path, lines] of Object.entries(files)) {
  const target = join(root, path);
  if (!existsSync(target)) {
    writeFileSync(target, `${lines.join("\n")}\n`);
    console.log(`wrote ${path}`);
    continue;
  }
  const text = readFileSync(target, "utf8");
  if (/^NODE_ENV=/m.test(text)) {
    console.log(`keep ${path}`);
    continue;
  }
  writeFileSync(target, `NODE_ENV=development\n${text}`);
  console.log(`added NODE_ENV=development to ${path}`);
}
```

The guard refuses `deploy` and `destroy` without an explicit `--stage`. Outside CI it also requires the profile named exactly after this project (`--profile <name>` or `ALCHEMY_PROFILE`), so neither the `default` profile nor another project's profile is used; a similar name such as `<name>-v2` belongs to another project and is refused. It also refuses while `CLOUDFLARE_*` variables are set in the shell, because alchemy would prefer them over the profile. In CI it uses no profile: it requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from the repository's secrets and refuses a named profile. When it proceeds, it selects the Cloudflare state store. `--guard-only` runs the same checks and prints the alchemy command instead of running it. Configure deployment separately under explicit user authorization.

### Write `scripts/alchemy-guard.ts`

```ts
// Runs `alchemy deploy` or `alchemy destroy` only with an explicit stage and this
// project's own credentials, so an ambient ~/.alchemy profile (including another
// project's production profile, or the `default` one) is never used.
//
//   bun run deploy -- --stage <stage> --profile <project>
//   CI with CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID: bun run deploy -- --stage <stage>
//   --guard-only: check, print the alchemy command and exit without running it
import { spawnSync } from "node:child_process";
import { readFileSync } from "node:fs";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";

const root = join(dirname(fileURLToPath(import.meta.url)), "..");
const project = JSON.parse(readFileSync(join(root, "package.json"), "utf8")).name as string;
const [command, ...given] = process.argv.slice(2);
const guardOnly = given.includes("--guard-only");
const rest = given.filter((arg) => arg !== "--guard-only");

function refuse(reason: string): never {
  console.error(`refusing to ${command ?? "run"}: ${reason}`);
  console.error(`usage: bun run ${command} -- --stage <stage> --profile ${project}`);
  process.exit(2);
}
function option(name: string): string | undefined {
  const index = rest.findIndex((arg) => arg === `--${name}` || arg.startsWith(`--${name}=`));
  if (index < 0) return undefined;
  const arg = rest[index]!;
  return arg.includes("=") ? arg.slice(arg.indexOf("=") + 1) : rest[index + 1];
}

if (command !== "deploy" && command !== "destroy") refuse("expected deploy or destroy");
const stage = option("stage");
if (!stage || stage.startsWith("-")) refuse("no explicit --stage");
const ci = process.env.CI === "true" || process.env.CI === "1";
const profile = option("profile") ?? process.env.ALCHEMY_PROFILE;
let args = rest;
if (ci) {
  if (profile !== undefined)
    refuse("CI uses the repository's secrets, not a profile; remove --profile and ALCHEMY_PROFILE");
  if (!process.env.CLOUDFLARE_API_TOKEN || !process.env.CLOUDFLARE_ACCOUNT_ID)
    refuse("CI needs CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID from the repository's secrets");
} else {
  if (!profile) refuse(`no explicit --profile (or ALCHEMY_PROFILE) naming the profile ${project}`);
  if (profile !== project)
    refuse(`profile "${profile}" is not this project's; the profile must be named ${project}`);
  if (process.env.CLOUDFLARE_API_TOKEN || process.env.CLOUDFLARE_ACCOUNT_ID)
    refuse(
      "CLOUDFLARE_* variables are set in this shell and would win over the profile; unset them",
    );
  if (option("profile") === undefined) args = [...rest, "--profile", profile];
}
const infra = join(root, "packages/infra");
if (guardOnly) {
  console.log(`would run in packages/infra: alchemy ${[command, ...args].join(" ")}`);
  process.exit(0);
}
const result = spawnSync(join(infra, "node_modules/.bin/alchemy"), [command, ...args], {
  cwd: infra,
  stdio: "inherit",
  env: { ...process.env, ALCHEMY_STATE: "cloudflare" },
});
process.exit(result.status ?? 1);
```

## Tests

`vp test` fails when no test exists, and the scaffold has none. One API test calls the router directly; one web test renders the landing page on the server, inside a memory router so the page may use `<Link>`, without a running API.

### Write `packages/api/test/router.test.ts`

```ts
import { ORPCError, call } from "@orpc/server";
import { describe, expect, test } from "vite-plus/test";

import type { Context } from "../src/context";
import { appRouter } from "../src/routers/index";

// The API answers without a session and refuses protected data to anonymous callers.
const db = {} as Context["db"];

describe("appRouter", () => {
  test("healthCheck answers OK without a session", async () => {
    expect(await call(appRouter.healthCheck, undefined, { context: { session: null, db } })).toBe(
      "OK",
    );
  });

  test("privateData refuses a caller without a session", async () => {
    const result = call(appRouter.privateData, undefined, { context: { session: null, db } });
    await expect(result).rejects.toBeInstanceOf(ORPCError);
    await expect(result).rejects.toMatchObject({ code: "UNAUTHORIZED" });
  });
});
```

### Write `project-rules/skills/verify-__PROJECT__/SKILL.md`

````markdown
---
name: verify-__PROJECT__
description: Verify __PROJECT__'s web app and API on the default stack. Use for every story that changes code, tests, configuration, scripts or rules.
---

# Verify __PROJECT__

## Setup

Bun 1.4.2, Git and `aep` on PATH. No Cloudflare account and no alchemy profile are needed or used. Work in the attempt's worktree, created outside the checkout (`aep dispatch start … --worktree ../__PROJECT__.worktrees/<story>`), so tools do not resolve configuration from the checkout above it.

## Checks

`aep verify plan --story <id>` lists the configured checks; `aep verify run --story <id>` runs them in this order on the committed candidate: `install` (`bun install --frozen-lockfile`), `aep-records` (`aep check`), `check` (`bun run check`: format, lint and type checks), `test` (`bun run test`), `build` (`bun run build`). CI runs the same commands except `aep check`.

## Operate the product

1. `bun run dev` starts the web app on http://localhost:3001 and the API on http://localhost:3000 with a local D1 database. It writes `apps/server/.env` and `apps/web/.env` when missing.
2. The landing page answers 200 at http://localhost:3001/ and the API answers `OK` at http://localhost:3000/.
3. Sign up with `POST http://localhost:3000/api/auth/sign-up/email` (JSON `name`, `email`, `password`, header `Origin: http://localhost:3001`) and keep the session cookie; `POST http://localhost:3000/rpc/privateData` with body `{}` answers 200 with the cookie and 401 without it.
4. When the change touches the web app, open the landing page, sign up, sign in and open the dashboard in a browser.
5. To run it in the background, start it as its own process group and stop the whole group: `set -m; bun run dev > dev.log 2>&1 & echo $! > .dev.pid; set +m`, then `kill -TERM -- -"$(cat .dev.pid)"`. alchemy's sidecar and `workerd` stop with it. Do not look the process up by a command-line pattern, which also matches your own shell and other checkouts.

`bun run deploy` and `bun run destroy` must refuse without `--stage` and the profile named exactly `__PROJECT__`; `bun run deploy -- --stage pr-1 --profile __PROJECT__ --guard-only` shows what would run without deploying.

## Evidence

Text reports go under `project-ledger/evidence/`; screenshots and other binary evidence under `project-ledger/evidence/<story>/` (follow the project evidence policy). Record the commands, their results and what was not exercised.
````
